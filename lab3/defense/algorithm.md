# Конспект для защиты расчетно-графической работы (Тема: OpenCL)

## 1. Постановка задачи (Что мы ищем?)

В рамках лабораторной работы реализуется поиск **компактной треугольной подматрицы заданного размера S с минимальной суммой элементов** внутри большой родительской матрицы размерностью Rows × Cols (например, 2500 × 2500 или 10000 × 10000).

### Главная геометрическая особенность:
Согласно техническому заданию, *«элементов выше главной диагонали нет в отличие от обычного понимания треугольной матрицы»*. Это означает, что искомый объект представляет собой **компактный нижний треугольник**. 

Если мы визуально выделим квадратное окно размером S × S, то алгоритм должен складывать только те элементы, которые лежат на его главной диагонали и строго ниже неё. Все элементы, расположенные выше главной диагонали данного окна, полностью игнорируются.

**Визуальная схема для размера S = 4:**
Если вершина (верхний левый угол подматрицы) находится по координатам `(r, c)`, то расчет затрагивает только элементы, отмеченные символом `X`:

```text
(r, c) ──>  X  .  .  .
            X  X  .  .
            X  X  X  .
            X  X  X  X
```
* `X` — элементы родительской матрицы, которые **участвуют в суммировании**.
* `.` — элементы, которые **полностью игнорируются** алгоритмом.

Количество элементов внутри такого треугольника рассчитывается по формуле арифметической прогрессии: 
$$\text{Количество элементов} = \frac{S \times (S + 1)}{2}$$
При заданном размере $S = 10$ в каждом проверяемом треугольнике суммируется ровно **55 элементов**.

## 2. Описание алгоритмов решения

Задача решается двумя независимыми методами (последовательным на CPU и параллельным на GPU OpenCL), результаты которых впоследствии сравниваются встроенным валидатором.

### А. Последовательный алгоритм (На CPU в модуле `utils.c`)
Центральный процессор выполняет вычисления классическим последовательным перебором пространственных координат (ячейка за ячейкой):
1. **Двухмерное скольжение окна:** Внешний цикл `for (r = 0; r <= rows - S; r++)` и вложенный `for (c = 0; c <= cols - S; c++)` перемещают верхний левый угол треугольника по матрице. Ограничение `- S` необходимо, чтобы искомая фигура не выходила за правый и нижний края родительской матрицы.
2. **Внутреннее суммирование:** Для каждой фиксированной позиции `(r, c)` запускаются два локальных цикла, обходящих нижнетреугольную область подматрицы:
   * Переменная `i` (от `0` до `S-1`) отвечает за спуск по строкам подматрицы.
   * Переменная `j` (от `0` до `i`) осуществляет проход по столбцам. Условие `j <= i` аппаратно отсекает верхнюю часть окна, гарантируя нижнетреугольную форму.
3. **Редукция данных:** Если посчитанная сумма строго меньше текущего глобального минимума, алгоритм обновляет минимальное значение. Если сумма равна текущему минимуму, инкрементируется счетчик количества найденных экстремумов.

### Б. Параллельный алгоритм (На GPU в модулях `kernel.cl` и `opencl_runner.c`)
Графический процессор (*NVIDIA Quadro 5000*) принципиально отличается от CPU: вместо последовательного перебора он разворачивает в видеопамяти **двухмерную сетку из миллионов независимых потоков (Work-items)**, выполняющихся параллельно.

1. **Пространственное отображение:** Каждый отдельный поток вычисляет глобальный идентификатор столбца `c = get_global_id(0)` и строки `r = get_global_id(1)`. Таким образом, один поток жестко привязан к одной конкретной координате матрицы и берет её в качестве вершины треугольника.
2. **Фильтрация и Padding:** Так как GPU оперирует аппаратными блоками — локальными группами потоков (`Work-groups`, размер задан флагом `-g 16` как блоки $16 \times 16$), глобальная сетка округляется в большую сторону до ближайшего кратного числа (`padded_rows`, `padded_cols`). Потоки, попавшие в область дополнения (вышедшие за рамки реальной матрицы), мгновенно отсекаются по условию `if`, записывая в ячейку ответа маркеры невалидности (координаты `-1` и максимальное число `0xFFFFFFFFFFFFFFFFUL`).
3. **Локальный просчет:** Валидные потоки параллельно запускают внутренние циклы суммирования нижнего треугольника (абсолютно идентичные логике CPU) и сохраняют вычисленную 64-битную сумму (`ulong`) в глобальную память GPU в плоскую таблицу по одномерному индексу: `linear_idx = r * padded_cols + c`.
4. **Многокритериальная редукция на хосте:** Рассчитанные массивы выгружаются обратно в ОЗУ хоста по шине PCIe. Центральный процессор производит финальный высокоскоростной анализ:
   * **Проход 1:** Находит минимальное число среди всех результатов.
   * **Проход 2:** Итерируется по сетке строго в лексикографическом порядке (строка за строкой, столбец за столбцом), подсчитывая точное число глобальных минимумов и фиксируя координаты **самого последнего** совпадения для выгрузки в файл.

## 3. Ответы на возможные вопросы при защите (Шпаргалка)

* **Вопрос: Зачем вы округляли размеры сетки OpenCL до кратности локальной группе?**
  * **Ответ:** Архитектура GPU требует, чтобы глобальная сетка потоков нацело делилась на размер локальной рабочей группы (в нашем случае $16 \times 16 = 256$ потоков в группе), так как аппаратно потоки выполняются блоками (Warp / Wavefront). Если размер матрицы (например, $2500$) не кратен $16$, физический запуск ядра будет отклонен драйвером (`Invalid Work Group Size`). Мы расширяем сетку до ближайшего кратного ($2512$), а внутри ядра ставим логический барьер `if (r + tri_size <= rows && c + tri_size <= cols)`, чтобы потоки-пустышки не производили некорректную запись в память.

* **Вопрос: Из-за чего возникала ошибка `Mismatch!` на больших матрицах и как вы её исправили?**
  * **Ответ:** Было обнаружено две причины. Первая — разница в разрядности системных типов данных: тип `long` в Linux (64 бита) отличается от `long` в Windows (32 бита), что приводило к разрушению выравнивания при чтении буферов на сервере. Мы зафиксировали инвариантный тип `int` для координат на хосте и GPU. Вторая причина — в больших разреженных матрицах существует огромное количество альтернативных подматриц с *абсолютно одинаковой* минимальной суммой элементов (например, множество нулей). CPU и GPU находили разные координаты, формально правые математически, но вызывавшие сбой валидатора. Мы перевели верификацию на многокритериальную основу: теперь программа считает точное количество таких минимумов, а при редукции гарантированно выбирает последнюю подматрицу по идентичному правилу индексов, что обеспечило статус `SUCCESS (Identical)`.

* **Вопрос: Что такое JIT-компиляция в OpenCL и с какой ошибкой вы столкнулись на Linux-сервере?**
  * **Ответ:** JIT (Just-In-Time) — это компиляция текстового кода ядра `kernel.cl` непосредственно во время выполнения приложения драйвером установленной видеокарты. Строгий компилятор NVIDIA CUDA на сервере (для видеокарты *NVIDIA Quadro 5000*) отклонил сборку ядра с ошибкой `error: 'long long' type is not supported` на строке инициализации заглушки максимума. Суффикс `ULL` и тип `long long` не являются стандартными для OpenCL C на GPU. Мы заменили константу на стандартную шестнадцатеричную маску `0xFFFFFFFFFFFFFFFFUL` (суффикс `UL` — `ulong`), что полностью решило проблему переносимости кода.

* **Вопрос: Почему на малых матрицах последовательная версия работает быстрее параллельной, а на больших — наоборот?**
  * **Ответ:** Это объясняется накладными расходами на вызовы OpenCL API. Инициализация контекста, JIT-компиляция ядра драйвером NVIDIA и, главное, пересылка данных по шине PCIe из ОЗУ хоста в видеопамять устройства занимают фиксированное очерченное время (порядка 0.4–0.5 сек). На малых объемах (матрица $100 \times 100$) CPU решает задачу за доли миллисекунды, выигрывая за счет отсутствия пересылок. Однако на матрицах большого масштаба ($10000 \times 10000$) объем вычислений возрастает экспоненциально, и CPU «вязнет» в миллиардах итераций. В этот момент GPU за счет огромной пропускной способности памяти и тысяч вычислительных ядер окупает латентность PCIe, обеспечивая кратное ускорение (Speedup Factor).
